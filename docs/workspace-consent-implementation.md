# 持久工作区授权与Run查询

2026-11-04；E03 schema 3在已有控制循环上增加本机工作区授权。它不代替云端ACL、OS文件选择器或安全书签验证。

`Journal::authorize_workspace`仅由可信Host在用户明确选择工作区后调用，绑定owner、request ID、实际目录身份、policy与授权环境摘要。同请求内容变化拒绝，撤销后的旧请求重放不会重新授权。每owner最多32个活跃工作区、1000个授权记录；当前没有删除幂等键来回收容量的接口。

工作区ID与资源身份不同：环境摘要仍保持原协议算法以兼容既有Run；新增资源摘要不包含可改名的路径或可重发的grant ID。Unix使用设备/inode与创建信息，Windows通过cap-fs-ext稳定API读取打开句柄的volume/file ID，不使用Rust仍属nightly的std扩展。Windows实际文件系统/目标机器尚未认证，尤其不能将此处的64位file ID当作ReFS 128位身份支持声明。

持久授权要求文件系统提供目录创建信息；缺失时明确拒绝，不凭可能被复用的inode恢复旧授权。临时capability的既有API保留，但不能冒充可跨重启恢复的持久授权。

目录替换会使原授权失效。同一资源存在unknown/dispatched调用时，即使撤销再授权或改名，也不能自动获得新执行权限；缺少工作区关联的旧unknown记录保守阻塞该owner新授权。没有提供“清除unknown后直接重跑”按钮。

私有Host目录总会加入拒绝范围。除规范路径检查外，还比较目录及祖先的物理身份，防止macOS Data卷别名绕过私有目录限制；检查绑定实际打开的目录能力，并确认路径未在授权过程中换成另一个对象。目录内的文件读取仍由既有逐组件no-follow、内容/大小和敏感名称规则控制。

`reserve_private_directory`供可信Host登记短路径IPC/缓存区域，须在写入秘密或恢复访问前调用。它拒绝与现有授权重叠、已变换的目录身份或未解决的执行记录，不会静默撤销用户选择来挪出私有空间；保护在当前Host内只增不减，重启时由Host配置再次登记。

`open_workspace`重新检查持久授权和目录身份，生成独立Run级grant。Run取消只撤销该Run的grant；工作区撤销则通过共享信号立即停止新许可，再在一个SQLite事务中撤销工作区、关联Run及在途调用，并写不可变审计。Host可以在等待Journal锁前触发`WorkspaceRevoker`，但只有持久事务成功才确认撤销；实际执行排空仍必须等待各Run的取消/租约，不把权限撤销当GPU释放。

关闭Journal会使本进程签发的工作区grant失效。重启可以依据仍有效的持久授权重新验证目录并取得新grant；已撤销记录、旧句柄和旧Run不会因此恢复。OS安全书签及进程身份由平台Host另行验证，模型不能调用这些授权方法。

`list_agent_runs`按owner及可选workspace分页，游标是规范十进制字符串，单页最多100项。只返回ID、状态、调用/步骤计数和active，不在列表里重新暴露prompt、工具内容或最终正文。

schema 1/2可前向迁移到3；不会凭旧Run推断工作区授权。旧schema2客户端不能读取schema3，发布/回退必须遵守数据格式门槛与备份恢复要求，不能假称已有无损降级实现。

`python3 scripts/check-workspace-store.py`在真实SQLite/文件系统下验证9项行为：幂等/owner隔离/私有根，撤销与重启，独立Run取消，预派发撤销信号，目录替换，未知执行重授权/改名拒绝，schema2迁移，真实macOS卷别名拒绝，以及私有IPC目录登记。模型响应为明确测试夹具；桌面OS文件选择器和云RunStore不由此认证。
