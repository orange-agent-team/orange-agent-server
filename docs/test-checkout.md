# Stripe 测试充值与订单恢复

此开发入口允许个人账户和组织 Owner、Billing 使用明确启用的测试商户档位。客户端提交档位和订单 UUID，金额、币种、购买微积分和测试商户由服务端确定。组织 Admin 可以按产品规则申请财务操作，直接充值要求 Owner 或 Billing。当前 HTTP 入口处理执行操作。用户 Web 的个人账户页提供创建、取消未派发订单、打开测试收银台及核对原订单的操作。[接口契约](../contracts/openapi/test-checkout.v1.json)

Unix 开发用户 API 通过 `ORANGE_STRIPE_TEST_CONFIG` 指向当前账户的私有 JSON 文件。字段为 `merchant_id`、`api_key` 和 `webhook_secret`。生产密钥无法启用此适配器。缺少配置时服务不挂载充值和回调路由。档位来自 `test_credit_offers`，价格字段为 Stripe 测试 Price 标识，现金使用币种最小单位，积分使用微积分。用户界面不接收卡号。API 版本固定为 `2026-11-18.endive`，当前接受普通单商户的测试卡 Checkout。真实商户资格、地区、方式和支付认证单列。

创建本地订单不会联系商户。用户确认派发时，服务先核对测试账户，再次检查当前用户及范围权限后原子领取一次派发权。平台在 Checkout 和 PaymentIntent 上附加同一订单和服务端生成的派发标记。明确尚未派发时可取消。已发出请求但响应不确定时保留原订单并等待权威对象；同一订单不会触发第二次创建会话。用户从收银台返回只会查询当前账户下的原订单。[Stripe Checkout 会话创建](https://docs.stripe.com/api/checkout/sessions/create) · [Stripe v1 幂等行为](https://docs.stripe.com/api/idempotent_requests)

回调入口使用未改动的请求体核验时间戳和 HMAC-SHA256，限制请求体大小并支持多个 v1 签名。通过签名且与本地派发相关的事件先写入不可变 Inbox，再返回接收确认。事件金额不会直接入账。后台从同一商户重新读取 Checkout、档位明细、PaymentIntent 和已捕获 Charge，核对来源绑定、测试模式、币种、现金金额、退款及争议标志。只有完整匹配的成功付款才通过同一 PostgreSQL 事务增加购买余额并写入平衡分录与唯一履约凭证。重复与乱序事件可以查询同一付款。商户不可用时保留待核对工作，身份或计量证据不一致时进入复核。[Stripe 履约流程](https://docs.stripe.com/checkout/fulfillment.md?ui=full-page) · [原始请求体验签](https://docs.stripe.com/webhooks) · [Checkout 明细](https://docs.stripe.com/api/checkout/sessions/line_items)

本机验收命令为 `python3 scripts/check-test-checkout.py --web-repo ../orange-agent-web`。测试使用真实用户 HTTP、PostgreSQL、浏览器和隔离的本地商户协议替身。Chrome 丢弃会话派发后的成功响应，刷新后确认仍为同一订单，随后由后端复核入账。测试不会打开外部收银台。未覆盖真实商户沙箱凭据，原路部分退款、拒付冲正及长期财务对账仍有独立交付要求。

## 原购买来源与部分退款

59 号迁移按购买履约、钱包分录和 Job 冻结记录重建逐单余额。每笔购买分别保留可用、Job 冻结、已消费、退款冻结和已退五项。Job 优先消耗原有未关联购买余额，再按购买入账顺序分配到具体订单，部分扣费和取消都回到原来冻结的购买来源。本机 Worker 验收使用独立的历史购买凭证夹具：对 10,000 微积分的原单执行真实转写，结算后原单已消费 2,200；发布前撤权的另一单在同一回收流程结束后全部恢复。

60 号迁移支持原支付币种的测试退款。界面按现金最小单位输入退款额，同一订单同时只允许一笔未决申请。申请先冻结原单可用购买微积分，保留已消费和 Job 冻结的部分。累计退款现金为 R、原购买积分为 C、原现金总额为 A 时，对应积分为 `ceil(R × C / A)`。本次冻结量为前后两个累计值之差。现金最小单位不足以对应正的可退积分时拒绝申请。失败或未派发取消时沿原单解冻。确认成功后保留原交易，另记独立的平衡冲正分录。

用户在个人账户的测试订单记录中可找回原购买并申请退款。后台对账事项提供原订单、冻结积分、退款金额及不可变条款摘要。独立审批人核对同一份资料，执行授权只产生待派发记录。实际请求前再次核对批准权限、原 Charge 的币种、金额、已退累计额和争议状态。同一退款使用永久业务编号，已派发但结果未知时只查询原 Charge 下符合原绑定的 Refund；分页游标可持久恢复。签名通知只唤醒查询。原退款对象处于 pending 或 requires_action 时继续冻结，权威对象的最终成功或失败才改变账本。对账事项的关闭另走既有治理流程。[Stripe 退款状态](https://docs.stripe.com/api/refunds/object) · [退款创建](https://docs.stripe.com/api/refunds/create)

联合验收使用 `python3 scripts/check-test-checkout.py --web-repo ../orange-agent-web --admin-repo ../orange-agent-admin`。用户浏览器验证退款申请、刷新恢复、取消及原订单历史。两套独立 Admin 浏览器对同笔受保护的退款执行制单、复核和批准。测试另检查撤销审批权限、外部失败、并发派发、签名通知重放和回包丢失后不重复发送。商户响应全部来自本机协议替身。

## 测试拒付与新消费限制

61 号迁移使用独立的账户消费版本表。这样，持有旧版预编译钱包查询的数据库连接可以在升级后继续处理已冻结的任务。收到有效签名的拒付通知时，系统按测试商户与原 Charge 匹配付款凭证。匹配到已入账原单后，新正金额任务预留和新的测试收银台派发暂停。该限制位于数据库和用户 API 中。零预留、读取既有账单和任务、确认已经发出的退款分别适用原有权限。若拒付先于购买履约到达，原 Charge 的购买积分在商户复核前保持未入账。不同业务回调共用商户事件编号登记，同一事件编号不能解释成两种付款事实。

处理器从固定测试商户读取 Dispute 对象，核对环境、原 Charge、PaymentIntent、金额和币种；原始通知中的状态仅用于安排读取。每次领取取得新的代次，超时后返回的旧结果无权覆盖较新的结果。商户确认 won、prevented 或 warning_closed 时只解除对应事项的限制。其余未结、上诉、已败诉或证据不符的事项保留核对。每个事项都有业务编号，更新不会改写原购买、任务结算、提供方收益或钱包流水。操作员可在对账事项中查看关联编号。已败诉而尚有损失的生产处理仍需独立的纠错权限与凭证。[Stripe 拒付对象与状态](https://docs.stripe.com/api/disputes/object) · [读取权威拒付对象](https://docs.stripe.com/api/disputes/retrieve)

账户页通过 `GET /api/v1/owners/{owner}/spending-status` 查询允许或暂停的新消费状态。刷新原订单查询时，不会重发购买。可执行的本地用例包括真实 CPU 转写已消费 2,200 微积分后发生拒付、在途查询被新代次取代、两个事项独立解封、先拒付后充值，以及浏览器显示支付争议期间仍可读取已有订单。

## 每日测试商户对账

64 号迁移随服务端启动执行。Unix 上的 orange-user-api 配置开发用 ORANGE_STRIPE_TEST_CONFIG 后，独立调度器每五秒尝试一页。重启沿用数据库中的商户、窗口、阶段和游标。首次扫描从系统登记商户或已有本地首笔订单两者中较早的 UTC 日开始。每次结算一个已经结束的 UTC 日，附带前一天的重叠扫描，区间均为左闭右开。系统登记前且没有本地订单可定位的旧账期需另行导入。

每个远端分页先确认账户，再以固定版本、时间过滤及游标读取最多 100 条余额流水。金额为带符号的最小货币单位。按结算币种、商户分类和可用状态分别汇总毛额、手续费和净额；跨币种购买保留原币、结算币和业务编号，交由运营核查。真实商户接入及其外部凭证尚待独立认证。[余额流水列表](https://docs.stripe.com/api/balance_transactions/list) · [余额流水对象](https://docs.stripe.com/api/balance_transactions/object)

后续阶段从原始购买、退款凭证和账本分录双向匹配。任务核查覆盖使用本商户购买批次且已提交交付的任务，会计入该任务所有来源的冻结、归还、提供方待入账和平台费用。日报的平台总额覆盖所有已结算任务。追加执行次数指同一任务在先前尝试后再次领取执行。已发布对象的逻辑占用按报告日内存续的秒数乘以对象字节数计算，未接入基础设施发票时存储和带宽现金成本为 null。

每页通过数据库租约领取。商户请求超时、返回无效凭证或数据写入失败时，扫描停留在最后一个已提交游标。失败代次、阶段和原因留存在 test_statement_failures。封存报告后才推进账期。同一差异以商户、类型和业务编号去重，已归属账户的差异生成对账事项，后续窗口追加带摘要的独立观测。扫描只能写入对账事实和事项。已派发退款需要读取原退款进行业务收敛，资金纠正须另经审计和相应授权。

本机验证命令为 `python3 scripts/check-merchant-statements.py --admin-repo ../orange-agent-admin`。它使用可销毁的 PostgreSQL 库、开发身份服务、两个不同权限的 Chrome 会话和回环商户协议替身。实际 Worker 任务分账随 `python3 scripts/check-transcription-input-grants.py --six-journeys-only --web-repo ../orange-agent-web` 检查；该命令需要已准备的本地 CPU 模型和开发证书。向测试专用扫描器提供当日关闭窗口可立即读取任务结果，原购买、退款、任务和账本时间戳保持原值。

## 从计量事实到开发积分入账

65 号迁移为经过服务端计量的文本和转写交付登记凭证。事件编号沿用响应提交的 commit_id。数据库以原 Job、提交编号、响应摘要和归属账户关联事实。计量接收、报价与测量校验、入账各自产生顺序记录。只有带原业务编号的真实账本事务成功提交，凭证才进入 posted。旧版已经结算的任务在升级时复用原账本编号、交付摘要和时间，结果可与原钱包、预算和所有分录逐项核对。

开发策略 development-v1 为每一轮设置六小时窗口、最多十二次处理。首次临时失败可以立即恢复，其后按五秒基数递增，最长间隔十五分钟。原因、轮次和尝试编号可回查。永久校验错误、超过期限或耗尽尝试都会产生关联原事件的事项；未明确的费用继续冻结。合法会话提交了无效的计量候选时，审核记录仅保留上传编号、归属、两个摘要及原因。在可信发布前出现的无效输入单独追踪。

财务操作员可在原事项申请重新核对计量，独立财务审批人读取同一事件的当前凭证后批准。执行该操作只开启新的重试轮次；任务、原计量事件和账本业务编号继续沿用。处理器重新验证原报价和消费方，使用原账本路径入账。服务端会拒绝其他事项或事件的编号，已经入账的事件无法重开。核对仍在进行时不能关闭相应事项。

使用 `python3 scripts/check-metering-retry.py --admin-repo ../orange-agent-admin` 在临时 PostgreSQL、真实 CPU 模型和两个 Chrome 会话上验证。上一版事故恢复演练使用 `python3 scripts/check-metering-upgrade.py`；它从本地 Git 的固定版本构建 schema 64、产生原始业务分录、运行当前迁移并检查钱包、预算和账本快照。两项面向本地测试积分，硬件、商户和生产稳定性仍需独立凭证。

## 贡献收益的等待期与审核

66 号迁移按原 Job 保存供应者净微积分、原结算事务和最早可审核时间。源账本给供应者记入 pending 后至少经过 24 小时，开发用户 API 的定时任务才登记待审核事项。并发扫描对相同 Job 只产生一项。可通过个人会话的 GET /api/v1/account/earnings 按结算时间和 Job 编号翻页。用户看到自己的净收益、等待期和当前状态，其他账户的游标会被拒绝。

财务管理员从该供应者的事项制单，另一位财务管理员查看原任务、原结算事务和净微积分后批准。执行时服务端再次核对等待期、归属、付款争议、节点限制、计量凭证和当前余额。消费与供应归属相同、实际提交人给自己供给、供应者与付费团队有关联时继续冻结。旧库中的团队交易如缺少结算时的成员证据，会标记需要历史核对。节点正常或原交易争议解除后，仍须按当前状态核验。

转可用由一笔平衡事务借记供应者待入账账户、贷记同一供应者可用贡献账户，原 Job 只能转一次。钱包中待入账余额必须和所有尚未释放的原始收益一致。取消使用可用收益预留的任务后，退回同一贡献积分账户。此流程只操作开发微积分。

完整联调使用 `python3 scripts/check-transcription-input-grants.py --six-journeys-only --provider-earnings --web-repo ../orange-agent-web --earning-admin ../orange-agent-admin`。测试以两个真实 CPU 转写订单和原结算为基础，在一次性数据库内仅加速收益审核时钟，另用固定的 100 微积分报价验证可用收益的预留和取消。生产风控和真实 24 小时运行观察仍需独立验收。
