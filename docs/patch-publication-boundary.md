# 现有文件编辑发布边界（未开放工具）

当前实现包含实际源预览、独立持久编辑同意、精确批准、安全属性绑定、发布前保留计划，以及 Apple 平台受信 Host 的实际发布。普通 Agent、CLI、Desktop 尚未注册 apply_patch；发布测试只修改自有临时文件，没有操作真实用户目录。

schema10 的 `editing_publications` 与 operation 的 intended→dispatching 在同一个 SQLite FULL 同步事务中提交。记录包含操作、批准预览摘要、目标路径、两个独立随机且受路径策略保护的暂存/原文件保留名称、原/结果 SHA，以及保留容量；另有资源身份和 Host epoch。记录不可更新或删除，事务失败时操作仍为 intended，原批准保留。

返回的 `PatchDispatch` 不可反序列化或克隆，持有当前读取/编辑租约；从数据库读取的 PublicationPlan 仅用于恢复展示，不能恢复执行权。再次派发拒绝。Host 重开后 dispatching 进入 unknown，旧 token/授权不复活；未决操作使同资源的新编辑保持隔离。元数据查询按已认证 owner 过滤，不读取文件内容。

当前保留上限为每个本地 Host 的物理资源 64 份计划及 64 MiB 估算量，包含源/结果内容和双方安全属性的保守余量。这是准入限制，不是磁盘 block quota；不代表多个 Host 的全局配额。历史完成记录也继续占用，后续只有在真实备份保留/人工恢复/明确释放流程完成后才可实现有证据的容量释放，不能先删除未知记录解除限额。

实际 SQLite/临时文件测试覆盖：重开保留、owner 隔离、未知不重派、数据库失败全回滚、源修改/撤权拒绝、计划不可改删、数量和字节两个限额。容量测试明确使用合成的终态操作记录，仅证明保留计划计数，不证明文件已经发布。测试先后暴露了未决资源隔离及 invocation/call 唯一约束，均调整测试夹具保持保护规则，没有放宽生产约束。

## schema11 实际发布

`publish_patch_dispatch` 消费不可复用的 token，先重验当前授权、审批有效期、Host epoch、原完整模型响应和实际源身份。同步 API 必须由拥有 Journal 的阻塞执行通道调用；尚未接入普通 Agent 的异步执行器，不宣称磁盘 I/O 超时或可取消保证。

流程依次持久记录 stage_intent、staged、capture_intent、captured、publish_intent、published、confirmed 七个阶段。暂存文件 create_new，复制内容及完整已建模的安全属性并同步。捕获原文件和发布新文件均使用 NOREPLACE；持有 fd、命名对象、父目录、内容和属性多次检查。最终步骤和成功 receipt 在同一事务中提交。

原 inode 保留在不可由普通工具访问的随机保护名称下，不在成功后自动删除。竞争目标不会被覆盖；旧 fd 在确认之后仍写入的内容保留于原 inode。不能声称持续监测了这些后续写入。捕获与发布之间存在目标路径缺口；中途失败可能留下缺口，操作为 unknown，所有版本保留，禁止猜测恢复、自动重试或覆盖回滚。

本机实测正常发布、ACL/xattr/mode 保留、竞争目标三版本保留、旧 fd 写入、源变化、暂存名冲突、撤权、审批过期、最终 receipt 写入失败。另使用独立真实测试子进程在六个边界直接 exit（含 rename 已发生但完成阶段尚未落库的窗口）；父进程重开 Journal 后均为 unknown，保留对应文件和阶段且不自动恢复。此证据不等于断电/文件系统故障认证。

`patch_recovery_view` 提供按 owner 隔离的只读日志视图，核对阶段连续性和已提交 receipt 摘要。区分最后持久化 intent、已记录的 publication 和已确认结果；不会把 intent 当作文件已经移动或发布。该查询不打开工作区、不返回文件内容、不授予恢复权限，也不能代替当前文件的实际检查。

Apple 平台的 `inspect_patch_recovery` 要求当前明确读取能力与计划的 owner、policy、物理资源身份一致，然后在受限阻塞任务中检查三个名称。只有计划固定的两个受保护名称可被这个内部检查器访问；模型参数不能提供任意保护路径。符号链接、非普通文件、硬链接、超限文件拒绝；父目录身份、打开对象和读取过程均重验。返回内容摘要、字节数、安全属性摘要及是否为原 inode/匹配原或新内容，不返回文件内容。读取租约保持至 receipt 丢弃，撤权后无法再次访问 snapshot，超时按既有能力规则隔离到排空。

恢复检查是有限时间内的观察，不能保证外部写入者之后不再修改文件。已确认 receipt 保持历史事实，当前原 inode 若遭后续写入，检查结果会独立显示摘要变化，不伪造历史 receipt，也不自动删除或恢复任何版本。测试覆盖未知路径缺口、旧 fd 后续修改、foreign owner/root、外部符号链接、撤权/排空及损坏结果摘要拒绝。

## 后续实现要求

1. 保留容量释放/归档、跨目标平台及产品界面；恢复决策的 Apple 内核实现见下方，不代表普通 Agent/桌面功能已经开放。不能丢弃仍被旧 fd 修改的版本。
2. 更广的父目录移动、文件系统错误、容量和跨进程权限实验；其他平台只能在真实实现/目标验证后开放。
3. 批准编辑的来源版本转换，保留撤权/删除校验；禁止为了允许编辑而关闭已有来源保护。
4. 接入普通 Agent/CLI/Desktop，独立编辑同意不得从只读或新建权限推导；保持产品逐次审批及完整响应屏障。

## schema12：单独授权的恢复决策

`authorize_patch_recovery` 只能由受信 Host 在独立的恢复/目录写入授权后调用；不接收只读或普通编辑 grant 作为权限转换来源。新的能力绑定 owner、policy、物理目录、原操作、随机环境和当前 Host epoch。重开 Host 或重新授权会使旧批准不能复用；撤权阻断后续派发和文件效果。

操作顺序为 `prepare_patch_resolution` → `approve_patch_resolution` → `dispatch_patch_resolution` → `publish_patch_resolution`。三个明确选择：保留当前普通目标文件；把保留原 inode 移到空缺的原目标；把暂存结果移到空缺的原目标。不存在“覆盖现有目标”选项。读权限仍独立检查，审批只接受该 owner 对确切摘要的确认，有效期不可原地延长。

预览不仅绑定内容和权限摘要，还绑定文件对象身份/时间摘要；同字节的新 inode 不能复用旧批准。请求键不可更改决策或观测版本，派发与审计在 SQLite FULL 同步事务内持久化。每个原操作同一时间仅允许一个恢复派发。恢复结果、历史批准及解决记录均不可修改或删除；结果和解决标记原子提交。

恢复文件动作使用 NOREPLACE，并保留未选中的其他版本。恢复原文件使用原 inode 的移动，已打开旧 fd 后续写入仍在该 inode 上，不用内容复制冒充原文件恢复。若旧 fd 在批准之前又写入，旧预览作废，必须重新查看实际版本。恢复进程退出或结果提交失败时只记录新的 unknown，不重试、回滚、删除或承认成功；下一次明确选择可以根据当前实际版本选择“保留当前目标”。

原模型操作仍为 unknown，不改写为 succeeded。只有确认的单独恢复结果能解除该文件操作自身造成的资源隔离。其他未知操作、未知模型调用和 `recovery_required` Run 的限制继续有效；不会自动恢复旧 Run 或恢复已撤销的普通权限。查看结果使用按 owner 过滤的 `patch_resolution_result`；它是历史结果，当前文件仍需检查。

恢复动作不释放保留容量，也不删除任何版本；发布配额仍保守计数。安全归档和容量交接尚待实现。同步文件效果 API 仍需由拥有 Journal 的阻塞执行通道调用，尚未接入普通 Agent 异步执行器、CLI、Flutter 或其他操作系统。

本机实际验证包含三种选择、ACL/xattr/mode、旧 fd 后续写入、同字节换 inode、错误 owner/policy/root、审批过期、撤权、旧 Host epoch、双恢复派发、数据库结果故障、保留原未知历史以及其他未知操作继续隔离。真实独立子进程在恢复动作前、rename 后和最终确认前分别直接退出；重开后均为 unknown，文件未被自动重放或删除。证据仅针对可用 macOS 文件系统和进程退出，未扩大为断电、所有文件系统或生产全工具认证。
