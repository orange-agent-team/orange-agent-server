# 人工确认后的来源连续性（schema28）

schema27回归实际复现了缺口：文件派生记忆经用户编辑后被标为user_declaration，fact_provenance和原始Store把它当作无来源数据，失去原工作区授权仍能读取。保留失败证据，修复的是Core来源判断，不是桌面按钮。

## 继承规则

新建的独立用户声明保持无外部来源；对同条目作人工确认或更新保留其已知前序依赖。origin仍表示谁确认内容，不是取消来源权限的授权。

memory_continuity顺序读取不可变已批准草稿，校验scope/entry/actor、规范化摘要、精确版本步进、Put类型和元数据边界。连续人工更新折叠到最近的模型版本；然后使用该版本原始模型请求和工具结果对应的来源图。纯用户声明链结束于最初独立声明，因此普通编辑不会每次增加图深度。遍历受原scope最多10000条草稿配额约束，缺失、不连续、损坏或超界历史明确拒绝。

原始Store也使用同一判断，并核对当前entry的origin/source_actor/source_run与不可变草稿一致。有继承来源的条目仍需来源感知API，不能通过Raw Store的read/list绕过。旧标题/正文不会因继承校验重新存回已清理的payload。

## 格式边界

schema28新增不可变human-source-continuity.v1策略标记，以及每条目已批准result_version的唯一索引。迁移保留全部旧草稿、工具结果、审批和目录快照；从既有expected_version等元数据重建来源，不重写已批准摘要。不合法重复版本导致迁移拒绝，不自动丢弃历史。

schema27及更早执行器会把人工确认错误地解释为无来源，因此必须拒绝schema28。当前执行器也在改写数据库前拒绝未知连续性策略。

## 实际验证

Runtime回归包含原红测试转绿、40次连续人工确认、独立用户声明仍可读、Raw Store拒绝、缺失历史拒绝和未知策略非修改式拒绝。

check-memory-compatibility.py --continuity把同一测试宿主分别链接固定schema27与新Runtime。旧程序实际执行文件读取、模型记忆写入、用户确认，并确认旧缺口确实存在；新程序打开同一库后要求原工作区授权，原授权撤回后再次拒绝，原始Store也拒绝。原操作、结果、来源引用和目录快照未重放或改写；旧程序UnsupportedVersion且数据字节不变。另保留普通v1记忆续跑与文件编辑升级检查。

模型响应来自明确脚本输送器，文件、SQLite、批准和撤权是真实本地执行。此结果不替代桌面记忆UI、真实本地LLM或其他OS/GPU/生产认证。
