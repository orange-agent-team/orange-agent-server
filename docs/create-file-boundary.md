# Create-only Agent capability — development implementation

The Rust Agent loop can explicitly negotiate `write_file` using `start_agent_creating`; legacy Runs retain their original tools. The desktop now consumes this capability through a fixed source release with explicit creation consent and per-file approval. This remains a development candidate and is not complete TK-06 editing support. The trusted Host must acquire separate OS access and durable create-only consent. Readonly grants cannot be converted to write grants. Each proposed file also requires exact per-operation approval.

## Contract and invocation

`CreateFileArgs` contains only `path` and `content`, rejects unknown fields, and limits UTF-8 content to 65536 bytes without NUL. It creates a new file only; existing destinations are never replaced, parent directories must already exist, and protected paths, links, private namespaces and traversal remain forbidden. Real path spellings and digests are preserved, including ordinary Unicode names.

`agent_creation_requirement(owner, run)` exposes only the owned immutable consent ID/version/environment needed for recovery; it does not restore or grant access.

The host first calls `authorize_file_creation(owner, request_id, policy, root)` after explicit user consent, or restores an existing consent with `restore_file_creation`. It then calls `start_agent_creating(config, messages, read, create, user_questions)` and `advance_agent_creating`. The consent must match the readonly workspace's physical resource, owner and policy. `approve_agent_creation` requires the exact operation ID, reviewed argument digest and bounded expiry. Generic readonly approval cannot approve creation. `revoke_file_creation` uses the exact consent version; signal all relevant handles before waiting for the journal lock, persist revocation, then drain leases before releasing OS access.

The developer CLI exposes `authorize-create REQUEST_ID`, optional private config `creation_consent_id`, `approve-create OP_ID DIGEST`, and `revoke-create VERSION`. Setting a consent ID only restores previously granted rights; it cannot create consent or upgrade a previously started readonly Run. The CLI never auto-approves. `show` provides the exact proposal for human review. Test harnesses approve only their own temporary fixtures.

## Durable boundary and recovery

SQLite schema5 records separate creation consent, immutable request keys and audit. Schema6 adds an immutable per-Run consent/version/environment binding. Schemas1–4 remain unchanged; migration does not invent rights. Current owner, physical directory identity, policy, consent version and Host epoch are checked. Journal reopening requires a fresh process capability; stale handles cannot execute. Consent quotas are32 active/1000 historical grants and8192 request keys per owner. Exact idempotent retries still resolve at the cap, while revoked request IDs never reactivate permission.

A complete model response is validated before any operation intent. The durable preview binds the same Run/invocation, response body/digest, call ID and exact arguments. Generic digest-only response or approval cannot bypass it. Dispatch and the runtime step increment commit atomically. Source lineage is revalidated before approval and execution. Both readonly and create-only permits remain held through publication and result commit; either revocation rejects publication when observed, and revocation acknowledgement must await draining. This does not promise atomic filesystem snapshot isolation against external user edits.

The publication primitive writes a private random staging file under a capability-relative parent, synchronizes and verifies bytes/inode, then performs no-replace rename. It synchronizes the directory before a durable success receipt. Failure handling never deletes or overwrites the destination. An uncertain publication/receipt outcome stays unresolved and is not replayed; reopening quarantines the resource and refuses fresh consent as a bypass. After receipt commit, context recovery applies one tool message without repeating the file effect. Historical metadata does not certify current file contents: later model requests and content-bearing recovery views revalidate actual created bytes, and deletion or changes prevent cached content re-exposure.

## Evidence and limitations

See `scripts/check-file-creation.py` for actual CLI restart, local HTTP adapter, SQLite and filesystem verification using explicitly scripted model/count responses. Runtime tests additionally exercise competing writers, symlink/protected-path refusal, expiry, permission revocation, schema migration, exact approval, context-commit interruption and post-publication receipt failure. These are not real-model quality results.

The atomic implementation currently targets Apple/Linux/Android; only available macOS has been exercised. Windows publication, Desktop OS write consent/UI, real model creation scenarios and the full cancellation/fault matrix remain required. No user directories, paid models, public deployment or real funds are used. Schemas5/6 are included in the fixed desktop candidate. Native and CLI tests use owned temporary databases; existing user data is not used as a migration fixture.

The host validation passed85 complete Runtime tests, strict Clippy for all Runtime targets, the new actual CLI/HTTP creation scenario, and the existing ask-user CLI regression. Evidence: `services_plan/execution/create-agent-host-validation.log` in the coordination workspace. These results do not certify Desktop integration or a real model.

CLI configured exclusions may include readonly shared model assets. They remain enforced by the readonly workspace capability; they are not registered as writable private state directories. Create consent and execution must match that independently checked physical resource. Journal private storage is always protected. The CLI fixture now includes a0755 excluded model-asset directory and rejects broad workspace selection before permission creation.

Integration evidence additionally includes125 shared-workspace tests, a real pinned7B read→exact new-file creation scenario with restart/no replay/confirmed stop, and desktop9 Rust/17 widget/5 native fixture scenarios. The real model previously returned model_unknown in one creation attempt; broad model qualification is not claimed. Actual macOS picker inspection remains unverified after the local computer-use channel failed; see the desktop creation boundary document and execution reports. Windows publication and the rest of the planned tool catalogue remain unfinished.
