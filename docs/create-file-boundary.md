# Create-only filesystem execution boundary — preparation

This is an isolated implementation slice, not a registered Agent tool or a Desktop write feature. Existing read-only grants cannot be converted to CreateFileGrant. The trusted Host must explicitly request process-local create consent, which is distinct from each operation's approval.

Journal.create_file verifies owner, policy, create environment, tool version, required approval and the exact content/path digest. The existing journal requires a committed response reference, records an intended operation and commits its dispatch before filesystem work. Missing/expired approval and tampered inputs have no target-file effect. This layer still relies on the trusted response adapter; concrete response-body/call provenance and persisted review UI must be connected during model-loop integration.

The supported publication primitive creates a private random staging file under the capability-relative parent, writes bounded UTF-8 content, fsyncs and verifies actual bytes and object identity, then uses no-replace rename. The destination is never overwritten or removed during failure handling. Directory sync, byte/identity checks and a durable result receipt must succeed before reporting creation. Any uncertainty after publication leaves dispatch unresolved and revokes the in-memory grant; reopen marks it unknown and refuses replay. A successful repeat returns the historical metadata receipt without rewriting a later user edit; it does not certify the file's present contents.

Normal Unicode paths retain their spelling; existing protected-name/link/traversal checks apply. Internal staging names are protected from workspace tools. The current atomic backend is for Apple/Linux/Android targets; only the available macOS target has been exercised. Other target implementations, persisted consent, write previews, source-lineage/recovery integration, model registration and Desktop OS write consent remain required. This slice must not upgrade existing read-only grants or be counted as complete TK-06 support.

Six focused real filesystem/SQLite checks passed: exact response/approval boundary, no overwrite, literal Unicode, protected paths/symlink/revocation refusal, journal failure after actual publication with no replay, two-host creation race with one complete winner, and expired/optional approval refusal.
