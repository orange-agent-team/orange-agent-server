# Create-only filesystem execution boundary — preparation

This is an isolated implementation slice, not a registered Agent tool or a Desktop write feature. Existing read-only grants cannot be converted to CreateFileGrant. The trusted Host must explicitly request durable create-only consent, distinct from each operation's approval. Opening a Journal restores descriptors only; the Host must explicitly reacquire OS access and restore a fresh process capability.

Journal.create_file verifies owner, policy, create environment, tool version, required approval and the exact content/path digest. The existing journal requires a committed response reference, records an intended operation and commits its dispatch before filesystem work. Missing/expired approval and tampered inputs have no target-file effect. The concrete preview is now persisted before approval and bound to the same Run/invocation, complete response body/digest and exact write_file call ID/arguments. Generic digest-only response/approval records cannot bypass it. The normal model loop and persisted review UI still need integration.

The supported publication primitive creates a private random staging file under the capability-relative parent, writes bounded UTF-8 content, fsyncs and verifies actual bytes and object identity, then uses no-replace rename. The destination is never overwritten or removed during failure handling. Directory sync, byte/identity checks and a durable result receipt must succeed before reporting creation. Any uncertainty after publication leaves dispatch unresolved and revokes the in-memory grant; reopen marks it unknown and refuses replay. A successful repeat returns the historical metadata receipt without rewriting a later user edit; it does not certify the file's present contents.

Normal Unicode paths retain their spelling; existing protected-name/link/traversal checks apply. Internal staging names are protected from workspace tools. The current atomic backend is for Apple/Linux/Android targets; only the available macOS target has been exercised. Other target implementations, persisted consent, write previews, source-lineage/recovery integration, model registration and Desktop OS write consent remain required. This slice must not upgrade existing read-only grants or be counted as complete TK-06 support.

Six focused real filesystem/SQLite checks passed: exact response/approval boundary, no overwrite, literal Unicode, protected paths/symlink/revocation refusal, journal failure after actual publication with no replay, two-host creation race with one complete winner, and expired/optional approval refusal. The complete Runtime suite subsequently passed68 tests and strict Clippy, including exact preview reopening, altered/foreign response refusal and generic-approval bypass refusal. No user directory, paid model, public service or real funds were used.


SQLite schema5 adds separate creation consent, immutable request keys and audit records without changing schemas1–4 or granting writes to existing readonly records. It binds current owner, policy, physical directory identity, consent version and Host epoch. Revocation signals stop existing capabilities before durable acknowledgement; failed revocation remains locally closed and cannot be mistaken for a committed removal. The Host must drain all relevant capabilities before releasing OS access. Historical request IDs cannot reactivate revoked consent. Unknown operations block renewed consent, including a new request ID for the same resource. Active writers also prevent a new private namespace from overlapping their root.

Consent inventory is bounded to32 active/1000 historical grants and8192 request keys per owner; an exact idempotent retry remains resolvable at the cap. Tests cover directory replacement, stale Host handles, readonly preservation, migration without implicit writes, revocation rollback, immutable history and request-key limits. The complete isolated Runtime suite now passes76 tests and strict Clippy. Normal Agent write capabilities, source-lineage/model integration, Desktop OS write consent and Windows publication remain unimplemented; schema5 is not applied to the formal Desktop or any user database by this preparation.
